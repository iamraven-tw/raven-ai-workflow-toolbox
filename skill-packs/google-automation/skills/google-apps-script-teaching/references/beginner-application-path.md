# 第一階段：生活應用入門課程

## 定位

第一階段使用真的能繼續使用的生活小專案，不用沒有情境的玩具函式。每個案例指定一個主要 Google App；必要時可讓另一個 Google App 擔任資料來源。預設不加入觸發器、Webhook、外部 API 或大型跨服務流程；唯一已確認的第一階段觸發器例外是案例四使用一個具 10 分鐘安全期限的時間觸發器，讓學生實際看到 Drive 定時檢查。

程式複雜度與工程測試由 Agent 負責。對使用者而言，每課都維持「完成必要設定、使用真正的選單／按鈕／表單、查看可見成果，出錯時複製繁體中文紀錄檔(Log)」的簡單流程。

共用開發環境關卡在進入本階段前完成，不算入課程案例。Script Properties 與 UI 基本操作也不獨立成課：

- 學員選定任一案例後，Agent 必須先完成該案例的「課前簡介」，再進入遠端建立、設定、推送、授權或 UI 操作。簡介要說明要解決的問題、完成後的成果、真實使用方式、Agent／學生分工、所需資源與設定，以及驗收方法。
- 每次推送到Apps Script(clasp push)成功後，第一次交付學生操作要在同一則訊息先提供「精簡課程回顧」，重述本案例功能、可見成果、目前操作的必要性與尚未發生的外部影響，再列設定或 UI 步驟。不得只剩操作步驟，也不得用精簡回顧取代案例開始時的完整課前簡介。
- 第一次執行真實案例時，才用白話介紹函式、函式選單、`執行`與`執行記錄`。
- 案例第一次需要 ID、Email 或其他設定時，才教使用者操作`專案設定`中的`指令碼屬性`。若設定的是 Google 資源 ID，先說明 ID 像資源的「門牌號碼」，能讓程式找到同一份資源；放在指令碼屬性可分開設定與程式碼、方便更換資源，並避免私人 ID 進入程式、紀錄檔(Log)或 Git。
- 每個案例仍保留正常、錯誤及重複執行測試，但由 Agent 執行並保存證據，不要求學生逐項操作測試函式。
- 每個案例需要的全新 Google 練習檔案，由 Agent 在取得遠端建立確認後直接使用最終教材名稱建立。不要要求學生先建立空白檔案，再另外執行改名。
- 每個案例通過可見成果驗收後，以一題簡短選擇題收尾。學生回答後，Agent 公布答案並說明原因；不論答對或答錯都能繼續下一個案例，不要求重答。

五個案例的已驗收程式已收錄於 `../templates/beginner/`，狀態與檔案清單以 `../templates/catalog.json` 為準。新的學生專案必須由 Agent 使用 `../scripts/materialize_template.py` 直接取用對應模板；不得再依本文件重新撰寫案例程式。本文件負責教學情境與驗收規格，不是程式生成提示。

學員選擇第一階段時，Agent 先在獨立的 `GoogleAppsScript/learn-gas-course` 工作區執行 `../scripts/update_course_progress.py --select-phase 1`。第一階段五個案例各自獨立、沒有相依順序；Agent 列出案例與完成狀態，讓學員自由選擇任一未完成案例，不得強制從案例一開始。第一階段不是第二階段的先修；若學員之後進入第二階段，就依固定順序完成第 1 至第 8 課，中途只允許中斷與恢復。

## 已確認案例一：家庭支出記錄表

### 主要 App

Google Sheets。

### 應用場景

使用者平常在`支出紀錄`工作表輸入日期、支出項目、分類、金額、付款方式及備註，再透過`支出工具`更新每月統計。`月度統計`工作表顯示本月總支出、分類統計、每月預算、剩餘預算及是否超支。

### 課前簡介（Agent 必須先說）

本案例會把日常支出整理成可持續使用的 Sheets 記錄表，完成後可以直接填支出，並從`支出工具`更新本月總額、分類與剩餘預算。Agent 負責建立版面、選單與安全測試；學生負責填一筆練習支出、操作選單並核對統計。第一次需要`MONTHLY_BUDGET`時，要先說明它代表學生自己的每月預算，放在 Script Properties 是為了日後只改設定、不改程式；本案例不需要 Google 資源 ID。驗收看`支出紀錄`、`月度統計`及繁體中文紀錄檔(Log)。

### 使用方式

1. 使用者執行`setupExpenseTracker`，建立必要工作表、欄位及自訂選單。
2. 使用者平常直接在 Sheets 填寫支出。
3. 使用者從`支出工具`選擇`更新本月統計`。
4. 使用者回到`月度統計`核對數字。

`MONTHLY_BUDGET`在統計功能第一次需要時才由使用者輸入指令碼屬性。重複執行不得重複建立工作表或欄位；金額不是數字或缺少設定時，必須用繁體中文說明並安全停止。

## 已確認案例二：批次信封版面產生器

### 主要 App

Google Docs。Google Sheets 只擔任寄件人設定與收件人清單的資料來源。

### 應用場景

適合公司寄送合約、發票與通知，或個人寄送掛號文件、活動邀請及節慶卡片。使用者可以一次準備多位收件人，批次產生可列印的信封版面。

### 課前簡介（Agent 必須先說）

本案例會把 Sheets 的寄件人與多位收件人資料，一次轉成可列印的 Google Docs 信封版面。Agent 負責建立程式、測試直式與橫式排版並保護已驗收基線；學生負責準備資料、選擇方向、產生文件並目視檢查。`SPREADSHEET_ID`來自本案例的資料來源試算表，它像試算表的「門牌號碼」，讓程式每次讀取同一份清單；要先說明網址位置與放進 Script Properties 的理由，再引導填寫。驗收看實際 Docs 的文字方向、位置、分頁與繁體中文紀錄檔(Log)。

### Sheets 資料

寄件人設定：

- 個人或公司名稱。
- 寄件人地址。
- 版面方向：`直式`或`橫式`。

收件人清單：

- 是否產生。
- 收件人名稱。
- 收件人地址。
- 備註。

### 使用方式

1. 使用者在 Sheets 填寫寄件人與收件人資料。
2. 使用者選擇本批次使用`直式`或`橫式`。
3. 使用者在 Apps Script 執行`generateEnvelopeDocuments`。
4. 程式為每位勾選的收件人產生一頁 Google Docs 版面。
5. `直式`依中華郵政國內直式信封書寫位置：收件地址直排在右、收件人直排置中、寄件資料直排在左下；收件與寄件郵遞區號分別位於右上及左下。
6. `橫式`依中華郵政國內橫式信封書寫位置：寄件資料在左上、貼郵票處在右上、收件資料在中央偏右；郵遞區號在地址上方第一行，姓名或商號名稱在地址下方。
7. Google Docs 沒有原生中文直書功能，程式以窄欄自然折行搭配無框線表格固定直式位置，不在每個字後插入手動換行。
8. 每位收件人的上方郵遞區號、中央內容與下方寄件資料必須放在同一個表格，並保留單頁安全高度；表格不得合併儲存格，郵遞區號放在既有寬欄並使用不可斷行連字號，避免位置重排或被拆成兩行。
9. 使用者開啟產出的 Docs，目視確認文字方向、五個資料區位置、每位收件人只佔一頁及每頁內容後再列印。

### 設定與安全

- `SPREADSHEET_ID`放在指令碼屬性。
- 姓名與地址只存在私人 Sheets 與產出的 Docs。
- 紀錄檔(Log)只顯示讀取、略過及成功產生的筆數，不輸出姓名或完整地址。
- 地址空白時略過該列並記錄中文原因。
- 測試單一、多位、直式、橫式及重複執行。
- 正常測試使用五筆政府官網公開的機關名稱與較長地址，搭配明確標示為虛構的測試姓名；官方來源記錄在範例 README，不使用機關真實人員姓名。
- 直式版面以[中華郵政國內直式信封書寫方式](https://www.post.gov.tw/post/internet/Postal/index.jsp?ID=210)為位置參考；收件人與收件地址字體使用 28，寄件人、寄件地址及「貼郵票處」使用 24，直式內容明確取消粗體與斜體。
- 直式版面完成學生目視驗收後視為定稿；後續橫式修改必須使用獨立排版函式、欄寬與列高，不得回頭改動直式已驗收基線。
- 橫式版面以[中華郵政國內橫式信封書寫方式](https://www.post.gov.tw/post/internet/Postal/index.jsp?ID=21002)為位置參考，每位收件人使用一個 3×3 無框線表格；地址優先依「縣市＋行政區」與其餘門牌分成兩行。
- 橫式收件地址與姓名字體至少使用 28，寄件地址與姓名使用 24；不得為了塞進版面而縮小已確認字體，應優先調整行距、分行與資料區尺寸。
- Google Docs 儲存格中的換行可能形成多個段落；字體必須套用整個儲存格文字，再逐段設定對齊與行距，不得只修改第一個段落。
- 保留 `testEnvelopeLandscape` 作為 Agent 的橫式版面回歸入口；測試暫時切換版面方向，產生五頁橫式文件後恢復使用者原本的方向設定。學生使用真正的 `generateEnvelopeDocuments` 產生橫式文件並目視驗收。
- `testEnvelopeLandscape` 產生文件後要讀回第一頁儲存格，逐字確認寄件資料實際為 24、收件資料實際為 28；只檢查原始碼中的數字不算字體驗收通過。
- 頁面方向測試必須同時驗證郵遞區號拆分、不可斷行連字號與直排資料沒有多餘空白或手動換行，遠端驗收再由學生目視確認實際文件。
- 本機測試要確認每位直式收件人只建立一個表格，且預定列高總和不超過單頁安全高度；Google Docs 沒有可靠的程式化實際頁數判讀，最後仍由學生目視確認郵遞區號沒有被拆到下一頁。
- 核取方塊的空白 `FALSE` 列不得影響最後資料列；沒有其他資料時，五筆教學假資料必須顯示在「收件人清單」第 2 至 6 列，讓學生不用捲動尋找。
- 重複執行前先辨識既有輸出，避免大量建立重複文件。

## 已確認案例三：教師隨機測驗與成績報表

### 主要 App

Google Forms。Google Sheets 擔任題庫與教師成績報表。

### 應用場景

適合學校老師、補習班、語言教師及公司教育訓練。老師長期維護一份 100 題題庫，每次考試由 Apps Script 隨機抽取 20 題，產生一份全班共用的 Google Forms 測驗。

第一版不為每位學生產生不同題目。全班使用同一份隨機 20 題考卷，降低管理、核對與除錯難度。

### 課前簡介（Agent 必須先說）

本案例會把 Sheets 題庫轉成一份全班共用、可自動計分的 Google Forms 測驗，之後再把成績更新回教師報表。Agent 負責題庫檢查、隨機抽題與工程測試；學生負責從`測驗工具`建立第一份表單、預覽作答並核對成績。`QUIZ_FORM_ID`來自學生透過選單建立的那份表單，它像表單的「門牌號碼」，讓後續更新沿用同一份測驗；Agent 要從已核對網址提供 ID 位置與完整值，並先說明放進 Script Properties 的理由。驗收看 Forms 題目、測驗結果、Sheets 成績報表與繁體中文紀錄檔(Log)。

### Sheets 題庫

每一列代表一題：

- 是否啟用。
- 題號。
- 題目。
- 題型。
- 選項。
- 正確答案。
- 分數。
- 答對說明。
- 答錯說明。

第一版只支援可以自動計分的單選題與是非題。題庫至少要有 20 題有效題目；不足時停止建立測驗。

### 使用方式

1. 老師在 Sheets 維護 100 題題庫；日後需要時可以再增加。
2. 老師在 Apps Script 執行`checkQuizBank`，檢查題號、選項、答案及分數。
3. 題庫檢查通過後，Agent 提供已核對的試算表連結；老師回到 Sheets，從`測驗工具`選擇`產生隨機測驗`。第一份表單必須從這個日常入口建立，不先執行`testQuizNormal`。
4. Apps Script 從啟用且有效的題目中隨機抽取 20 題，再打亂題目順序。
5. 程式建立一份全班共用的 Google Forms 測驗，最前面包含必填的`姓名`與`學號`，並將編輯及填寫網址寫入`測驗設定`。
6. Agent 讀取並核對表單編輯網址後，先說明 Form ID 是這份表單的「門牌號碼」；`QUIZ_FORM_ID`讓程式後續更新同一份測驗、避免重複建立，放在指令碼屬性則可在換表單時只改設定，不修改程式。接著提供可點擊連結、說明 Form ID 位於`/forms/d/`與`/edit`之間，並提供本次完整 ID；老師將`QUIZ_FORM_ID`存入指令碼屬性。
7. 老師執行`checkQuizFormSettings`確認設定；`testQuizNormal`由 Agent 驗收同一份表單，不列為老師操作。任何工程測試都不得在`QUIZ_FORM_ID`未設定時搶先建立第一份表單。
8. 老師親自預覽並完成一次測試作答，確認題目、答案、配分及即時成績。
9. 老師將同一個填寫網址分享給全班。
10. 需要教師總表時，老師從 Sheets 的`測驗工具`選擇`更新成績報表`；對應的程式入口是`updateScoreReport`。

### 成績報表

報表寫回教師使用的 Sheets，欄位包含：

- 提交時間。
- 姓名。
- 學號。
- 得分。
- 滿分。
- 百分比。
- 是否及格。

學生提交後由 Google Forms 立即計算成績；第一階段不建立提交觸發器。老師需要彙整時才手動更新報表。

### 設定、安全與測試

- 第一次建立測驗後，由使用者依共用流程將`QUIZ_FORM_ID`輸入指令碼屬性，後續更新同一份測驗。
- 姓名、學號與作答內容屬於個人資料，不得寫入紀錄檔(Log)或公開測試資料。
- 測試使用假姓名與假學號。
- 測試有效 20 題、題庫不足、缺少正確答案、分數錯誤、題號重複及重複執行。
- 重複執行不得在同一份 Forms 產生重複題目。
- 教學順序回歸測試必須確認`checkQuizBank`之後先使用 Sheets 的`測驗工具`建立第一份表單；Agent 的`testQuizNormal`只能在`QUIZ_FORM_ID`設定完成後驗收，不得取代老師日常使用的自訂選單，也不得要求老師執行。
- 立即公布成績時，預設只顯示分數，不在考試進行期間顯示正確答案。
- 第一版不為每位學生個別抽題、不自動寄信、不建立觸發器，也不使用 Web App。

## 已確認案例四：指定資料夾檔案上傳紀錄器

### 主要 App

Google Drive。Google Sheets 只擔任上傳紀錄表。

### 應用場景

適合收取客戶檔案、學生作業、活動照片或公司內部文件。使用者指定一個 Drive 資料夾；有人將新檔案上傳到該資料夾後，系統定期檢查並將上傳紀錄寫入 Sheets，方便確認何人、何時上傳了哪些檔案。

### 課前簡介（Agent 必須先說）

本案例會定期檢查一個指定 Drive 資料夾，把真正的外部上傳活動記到 Sheets；它不會移動、刪除或改名檔案。Agent 負責建立檢查流程、Drive Activity 設定、安全期限與測試；學生負責指定自己的測試資料夾與紀錄表、上傳測試檔案、啟用短暫自動檢查並在驗收後關閉。`WATCH_FOLDER_ID`與`LOG_SPREADSHEET_ID`來自學生指定的兩個既有資源，都是讓程式找到正確目標的「門牌號碼」；Agent 要協助從網址擷取、說明位置與 Script Properties 的理由。驗收看上傳紀錄、背景`執行項目`及觸發器已關閉的狀態。

### 必須先說明的限制

Apps Script 沒有「Drive 檔案上傳時」觸發器。本案例使用時間觸發器定期檢查，因此不保證上傳後立刻出現紀錄。

內建 Drive 服務只能直接取得檔案擁有者與建立時間，不能把它們說成上傳者與上傳時間。為了符合本案例需求，Agent 使用免費的 Google Drive Activity 進階服務查詢上傳活動。此服務可能因 Google 的隱私或權限限制而只回傳使用者識別碼，或顯示為無法辨識；不得猜測姓名或 Email。

本案例只把從電腦或裝置上傳的外部檔案視為「上傳」。將既有 Drive 檔案移入資料夾、建立全新 Google 文件或複製檔案都不是同一種活動，不得混在上傳紀錄中。

### 紀錄欄位

- 上傳者：可取得時記錄名稱或識別資訊；無法取得時明確顯示`無法辨識`。
- 檔案名稱。
- 檔案類型：顯示容易閱讀的中文類型，另保留 MIME type 供除錯。
- 上傳時間：使用 Drive Activity 回傳的活動時間。
- 偵測時間。
- 檔案網址。
- 檔案 ID：作為避免重複紀錄的依據。
- 處理狀態。

### 使用方式

1. 使用者建立一個專用測試資料夾與一份上傳紀錄 Sheets。
2. 使用者將兩個網址貼給 Agent；Agent 取出 ID，說明 ID 位於 URL 的哪一部分。
3. 使用者親自在`專案設定`的`指令碼屬性`填入資料夾 ID 與試算表 ID。
4. Agent 在程式與資訊清單中啟用 Google Drive Activity 進階服務。
5. 使用者執行必要的設定檢查與基準初始化並完成授權；Agent 已先完成正常、錯誤與重複工程測試。
6. 使用者親自將測試檔案上傳到指定資料夾，再從 Sheets 的`上傳工具`選擇`檢查新上傳`。
7. 使用者回到 Sheets 核對上傳者、檔名、類型及時間；確認手動日常入口正常後，再依引導建立時間觸發器。
8. Agent 先說明教學模式會每 1 分鐘檢查一次，能快速看到結果，但不適合長期開啟；免費個人帳號的觸發器每日總執行時間有限，因此完成驗證後必須立即關閉。Agent 顯示本次影響並取得確認。
9. Agent 在同一則操作指示提供已核對的 Apps Script、Sheets 與測試資料夾連結，接著一次說完：重新整理 Apps Script 編輯器與 Sheets → 從`上傳工具`選擇`啟用每分鐘檢查（教學 10 分鐘）`→ 立刻到測試資料夾上傳一個新檔案 → 等待一到數分鐘 → 回到`上傳紀錄`查看背景流程是否自動寫入。不得停在「已啟用」要求學生先回覆；程式只建立一個時間觸發器，重複啟用不得建立第二個，並顯示完成後要關閉的警告。
10. 這次背景驗收不再手動選擇`檢查新上傳`。學生看到自動新增的紀錄後，只需回覆簡短結果，再進入觸發器清理。
11. 使用者到 Apps Script 左側`執行項目`查看`runUploadCheckByTimer`的背景執行結果；Agent 必須在同一則操作指示提供已核對的 Apps Script 編輯器連結。
12. 驗證完成後，使用者立刻回到 Sheets，從`上傳工具`選擇`停止自動檢查`，再選擇`查看自動檢查狀態`，看到關閉狀態才算清理完成。
13. 如果學生忘記停止，程式會在啟用約 10 分鐘後的下一次背景執行移除教學觸發器。這只是安全保護，不取代教學生親自停止。
14. 若本次手動操作出錯，使用者到 Apps Script 編輯器下方的`執行記錄`複製文字；需要調查背景執行時，再開啟左側的`執行項目`。

### 設定、安全與測試

- `WATCH_FOLDER_ID`與`LOG_SPREADSHEET_ID`放在指令碼屬性。
- 第一次啟用時先建立基準點，避免把資料夾全部歷史活動誤當成本次新上傳。
- 每筆紀錄使用檔案 ID 與活動時間產生唯一識別；重複檢查不得新增重複列。
- 紀錄檔(Log)只顯示檢查結果、成功筆數、略過原因與錯誤原因，不輸出上傳者姓名、Email 或完整檔名。
- 測試單一檔案、多個檔案、不同檔案類型、沒有新檔案、重複檢查、移入既有 Drive 檔案、錯誤資料夾 ID，以及無法辨識上傳者。
- Agent 的觸發器回歸測試要涵蓋每 1 分鐘頻率、10 分鐘期限、重複啟用不產生第二個觸發器、期限遺失時安全停止、手動停止及舊版觸發器清理；學生不需要逐項執行測試函式。
- 每分鐘執行一天會觸發 1,440 次，只限短暫教學。正式使用預設建議每 15 或 30 分鐘，再依實際上傳量與配額調整；Apps Script 最新配額以[Google 官方配額說明](https://developers.google.com/apps-script/guides/services/quotas)為準。
- 第一版不移動、重新命名、刪除或修改任何檔案，也不變更分享權限。
- 建立時間觸發器前必須先取得使用者確認；觸發器由使用者從 Sheets 的中文自訂選單親自啟用。推送程式本身不得建立、更新或刪除觸發器。

### 免費額度與正式使用間隔

背景自動寫入成功並確認觸發器已關閉後，Agent 要把以下觀念當成本案例的收尾內容，不要求學生自行計算：

- 教學當下先核對[Google Apps Script 官方配額](https://developers.google.com/apps-script/guides/services/quotas)，因為 Google 可能調整數值。
- 目前個人 Gmail 帳號的安裝型觸發器每日總執行時間是 90 分鐘；這項配額按「使用者」計算，不是每個專案各有 90 分鐘。
- 安裝型觸發器使用建立者的帳號權限執行。同一個 Google 帳號即使在不同 Apps Script 專案建立觸發器，執行時間仍會加總到該帳號的每日額度；不同帳號各自計算自己的配額。
- `everyMinutes()`可使用 1、5、10、15 或 30 分鐘；一小時以上則使用小時型間隔。最新可用值以[Google 時間觸發器官方規格](https://developers.google.com/apps-script/reference/script/clock-trigger-builder)為準。

若假設同一帳號完全沒有其他觸發器，並把 90 分鐘全部留給一個專案，各間隔的理論值如下。這只是方便理解的上限，不是安全保證：

| 間隔 | 每日執行次數 | 平均每次最多可用時間 |
|---|---:|---:|
| 1 分鐘 | 1,440 次 | 3.75 秒 |
| 5 分鐘 | 288 次 | 18.75 秒 |
| 10 分鐘 | 144 次 | 37.5 秒 |
| 15 分鐘 | 96 次 | 56.25 秒 |
| 30 分鐘 | 48 次 | 112.5 秒 |
| 60 分鐘 | 24 次 | 225 秒 |

實務建議：

- 1 分鐘：只用於本案例這類短暫教學，不作為長期預設。
- 15 分鐘：只有少量簡單自動化、希望較快發現新檔案時使用。
- 30 分鐘：免費帳號的建議預設，較能保留額度給同帳號其他專案。
- 60 分鐘：同一帳號已有多個自動化，或不要求即時偵測時使用。
- 5 或 10 分鐘：先從「執行項目」量測實際執行時間並盤點其他專案，再決定是否長期啟用。

估算時要把同一帳號所有觸發器的執行時間一起保留安全餘裕；不能因為單一專案的試跑很快，就假設每天都會維持相同速度。

## 已確認案例五：個人化批次郵件寄送器

### 主要 App

Gmail。Google Sheets 只擔任待寄郵件清單與寄送結果紀錄。

### 應用場景

適合寄送課程通知、活動提醒、付款提醒、客戶通知或其他格式相近但需要加入收件人姓名的郵件。使用者先在 Sheets 填入每位收件人的 Email、姓名、預計主旨與內容，再從`郵件工具`選擇`批次寄送郵件`，程式為每封信加入個人化稱呼後批次寄出。

### 課前簡介（Agent 必須先說）

本案例會把 Sheets 中格式相近的通知加上每位收件人的姓名，再從`郵件工具`批次寄出並寫回結果。Agent 負責選單、欄位檢查、配額與防重複測試；學生負責先填自己的測試信箱、確認寄送筆數、真實寄出一次並到收件匣與`寄件備份`核對。本案例沒有 Google 資源 ID，但真實寄信會對外產生影響，所以在寄送前必須再次確認；測試 Email 是個人資料，不要求貼進對話。驗收看 Sheets 寄送狀態、實際郵件與繁體中文紀錄檔(Log)。

### Sheets 欄位

- Email。
- 姓名。
- 預計主旨。
- 預計內容。
- 寄送狀態。
- 寄送時間。
- 錯誤原因。

不設置`是否寄送`欄位。填入完整資料且`寄送狀態`空白，就代表準備寄送；已寄出的資料由狀態欄辨識並略過。

### 個人化規則

- 實際主旨：`「姓名」您好｜「預計主旨」`。
- 實際內容：先加入`「姓名」您好：`，再接上使用者填寫的預計內容。
- 第一版使用固定格式，不加入複雜的範本語法或 HTML 排版。

### 使用方式

1. 使用者在 Sheets 填入一筆自己的測試信箱、測試姓名、主旨與內容。
2. Agent 以`onOpen(e)`建立`郵件工具`自訂選單；使用者重新整理 Sheets 後，不需要建立圖片、繪圖或指派指令碼。
3. 使用者從`郵件工具`選擇`批次寄送郵件`後，程式先檢查所有`寄送狀態`空白的資料列。
4. 畫面顯示本次有效、錯誤及預計寄送的筆數；使用者再次確認後才開始寄信。
5. 程式逐筆寄送，並寫回`已寄出`、寄送時間或錯誤原因。
6. 使用者親自到測試信箱確認收件結果，再到 Gmail 的`寄件備份`核對主旨與內容。
7. 單封測試通過後，才使用少量假資料測試批次寄送；真實寄給其他人前仍須再次確認。

本案例以電腦瀏覽器中的 Sheets 自訂選單作為日常操作入口。

### 寄送安全

- 第一版每次最多寄送 10 封；超過時安全停止，不自動分批續寄。
- 使用只能寄信、不能讀取 Gmail 收件匣的`MailApp`。
- 寄送前檢查`MailApp.getRemainingDailyQuota()`；剩餘配額不足時不開始寄送。
- Email、姓名、主旨或內容缺漏時不寄送，並將原因寫回該列。
- 使用鎖定機制避免重複操作寄送選單造成同時執行。
- 寄送前先將該列狀態寫為`寄送中`，成功後才改為`已寄出`。
- 已是`已寄出`的資料永遠略過。
- 停留在`寄送中`的資料不得自動重寄；使用者先到 Gmail 的`寄件備份`查證，再交由除錯流程處理。
- 寄送前的畫面確認必須顯示寄送筆數，但不列出完整 Email、姓名或郵件內容。
- 紀錄檔(Log)只顯示開始、成功、失敗、略過筆數及中文原因，不輸出 Email、姓名、完整主旨或內文。

### 測試

- 欄位完整的一封測試郵件能寄到使用者自己的測試信箱。
- 實際主旨與內容都正確加入測試姓名。
- Email 格式錯誤、缺少姓名、缺少主旨及缺少內容時不寄信。
- 同一批包含有效與錯誤資料時，只寄送有效資料並正確寫回各列結果。
- 同一天剩餘配額不足時，在第一封寄出前停止。
- 重複選擇寄送功能不會重複寄送`已寄出`資料。
- 模擬`寄送中`狀態時不自動重寄，並用繁體中文指示使用者檢查`寄件備份`。
