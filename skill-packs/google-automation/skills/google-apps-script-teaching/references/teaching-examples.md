# 教學案例與共同規格

## 設計原則

教學模式使用同一個「活動報名與通知系統」逐步擴充，不讓初學者在每一課重新理解不同情境。三個案例合起來涵蓋 Google Sheets、Google Forms、Google Docs、Google Drive、Gmail、觸發器、Web App、Webhook、資料驗證與批次處理。

已驗收模板的取用、程式維護、終端機命令、本機檔案及正常／錯誤／重複執行等工程測試由 AI Agent 處理。使用者不需要親自寫程式、貼上程式、重新生成程式或逐項執行測試函式，只需學會活動報名與通知系統中當下必要的 UI 操作，親自完成真實使用流程、檢查 Google 服務中的實際成果，並處理必要的 Google 登入、OAuth、Script Properties 輸入及具外部影響的操作確認。沒有實際用到的介面不強迫教學。

教學說明一律以完全不懂程式語言的普通人為對象。Agent 使用短句、白話與一步一動作的方式引導，不要求使用者理解語法，也不一次解釋過多專有名詞。

## 案例一：報名資料收集

### 可見成果

使用者填寫練習用 Google Form 後，回覆會進入 Google Sheets；處理函式會驗證姓名、Email 與活動場次，並在工作表寫入處理狀態。

### 使用服務

- Google Forms
- Google Sheets
- 表單提交觸發器

### 練習概念

- 表單回覆與試算表資料列的關係。
- 必填欄位、Email 格式及允許值驗證。
- 正常資料、錯誤資料及空白資料測試。
- 每次處理只更新必要欄位。
- 從 Sheets 選單執行後，到 Apps Script 左側「執行項目」閱讀相符時間的中文紀錄檔(Log)。

## 案例二：文件與通知產生

### 可見成果

Agent 從尚未處理的報名資料批次建立 Google Docs，存入指定 Google
Drive 資料夾，再把確認文件以 PDF 附件寄到該筆報名資料的 Email；
教學驗收使用學員能親自收信的地址，重複執行不會重複建立文件或寄信。

### 使用服務

- Google Sheets
- Google Docs
- Google Drive
- Gmail
- 時間型觸發器

### 練習概念

- `getValues()`、陣列處理及 `setValues()` 批次寫回。
- 從指令碼屬性(Script Properties)讀取範本與資料夾設定；收件地址直接
  來自報名資料，不另設 `TEST_EMAIL`。
- 使用處理狀態或唯一識別碼避免重複結果。
- 寄到被處理報名資料的 Email；固定教材資料自動使用學員帳號，會進入
  真實寄送測試的表單資料則由學員填寫自己能收信的地址。
- 寄送前清楚確認，寄送後記錄狀態；不確定上次是否成功時停止，不自動重寄。
- 手動測試通過後才考慮建立觸發器。

## 案例三：外部資料入口

### 可見成果

簡單 Web App 可顯示測試狀態；`doPost(e)` 可接收不含敏感資料的測試 Webhook，驗證內容後寫入練習用 Google Sheets。

### 使用服務

- Web App
- Webhook
- Google Sheets
- `ContentService` 或 `HtmlService`

### 練習概念

- `doGet(e)` 與 `doPost(e)`。
- JSON 解析、必要欄位驗證及中文錯誤回應。
- 執行身分、存取權限及測試網址。
- Webhook 重送時不重複建立資料。
- 先做無遠端副作用的本機測試，再由 Apps Script 對實際 `/exec` 網址送出測試 POST。
- 部署前確認、使用實際網址驗證，完成後封存公開測試 deployment。

第一版 Webhook 只使用假資料，不接收密碼、付款資料、OAuth Token 或真實敏感個資。API Key、第三方 Token 與正式 Webhook 驗證只教導安全存放及設定檢查，不在第一版串接外部付費服務。

## Script Properties 共同規格

### 建議屬性名稱

依案例實際需求選用，不為未使用的服務建立多餘設定：

- `SPREADSHEET_ID`
- `FORM_ID`
- `DOC_TEMPLATE_ID`
- `OUTPUT_FOLDER_ID`
- `API_KEY`
- `THIRD_PARTY_TOKEN`

### 操作規則

1. Agent 先列出本課需要的屬性名稱、用途及是否敏感。
2. 第一次設定 Form ID、Spreadsheet ID、Document ID、Folder ID 或其他 Google 資源 ID 前，Agent 先說明 ID 是資源的「門牌號碼」：程式靠它持續操作同一份資源；使用指令碼屬性可讓設定與程式碼分開，換資源時不用改程式，也不把私人 ID 寫進原始碼、紀錄檔(Log)或 Git。
3. Agent 建立讀取設定及檢查缺漏的程式，但不得把實際值寫入原始碼。
4. 一般 Google 資源由 Agent 建立時，Agent 必須從已核對網址擷取 ID，說明它位於 URL 的哪一段，並直接提供可複製的完整值；不得要求學生自己拆網址。只有使用者原有或親自建立的資源，才由使用者主動貼 URL 給 Agent 擷取。
5. 使用者到 Apps Script「專案設定」的「指令碼屬性」，依序使用「編輯指令碼屬性」、「新增指令碼屬性」及「儲存指令碼屬性」親自輸入實際值。
6. Agent 不要求使用者把 API Key、Token、密碼、Client Secret、Webhook Secret、Private Key 或 OAuth 憑證貼進對話；這些值由使用者自行輸入。
7. `clasp`、Git 與範例檔案只保存屬性名稱或 placeholder，不保存實際值。
8. 程式只記錄「已設定／未設定」，不得把實際值輸出到紀錄檔(Log)。
9. Google 帳號密碼、OAuth access token 及 refresh token 永遠不得存放。

`SPREADSHEET_ID`、`FORM_ID`、`DOC_TEMPLATE_ID` 與 `OUTPUT_FOLDER_ID` 是專案設定，不等同密碼；仍採最小揭露原則，不在公開範例中使用真實值。

Script Properties 是避免把設定硬寫進程式與 Git 的基本做法，但不是專業秘密管理系統。擁有專案編輯權限的人可能透過專案或程式接觸到共用設定，因此不得把不應與專案編輯者共享的機密放入其中。

## 中文紀錄檔(Log)共同規格

### 狀態格式

主要函式至少輸出開始、成功及失敗紀錄；需要時加入設定、進度、略過及警告：

```javascript
console.info('[開始] 準備處理報名資料｜測試模式=true');
console.info('[設定] 必要的指令碼屬性均已設定');
console.info('[進度] 正在處理第 3 筆資料');
console.warn('[略過] 第 3 筆資料已經處理完成');
console.info('[成功] 已建立文件並寄出一封報名確認郵件');
console.error('[失敗] 無法建立文件｜原因：找不到指定資料夾');
```

### 撰寫規則

- 紀錄檔(Log)使用繁體中文，清楚說明目前步驟及結果。
- 可記錄函式名稱、測試模式、資料列、處理數量及非敏感識別資訊。
- 不記錄 API Key、Token、密碼、OAuth 憑證、完整郵件內容或不必要的個資。
- 發生錯誤時寫出失敗步驟及可採取的下一個檢查動作。
- 不只輸出原始物件或英文例外；Agent 必須補上初學者可理解的中文脈絡。
- 使用者從 Apps Script 編輯器直接按「執行」時查看下方的「執行記錄」；從 Sheets 選單、觸發器、表單或 Web App 啟動時，到左側「執行項目」查看相符時間。

## 每課測試規格

每一課至少完成下列工程測試與教學驗收：

1. **設定檢查**：必要 Script Properties 齊全時可執行；缺少時顯示中文錯誤，且不繼續寫入資料。
2. **正常案例**：一筆有效測試資料產生預期結果。
3. **錯誤案例**：空白或格式錯誤資料被拒絕，且紀錄檔(Log)說明原因。
4. **重複執行**：同一筆資料重跑不會產生重複文件、郵件或資料列。
5. **批次案例**：需要批次處理的課程同時測試零筆、一筆及多筆資料。
6. **真實 UI 驗收**：使用者以案例真正的選單、按鈕、表單、觸發器或部署入口完成一次代表性流程。
7. **可見結果**：使用者能在 Sheets、Docs、Drive、Gmail 收件匣／寄件備份或 Web App 回應看到結果。
8. **可診斷結果**：代表性操作的執行記錄或「執行項目」包含相符的中文紀錄檔(Log)；出錯時使用者複製文字給 Agent。
9. **收尾小問題**：實際成果驗收後問一題與本課核心概念有關的簡短選擇題。學生回答後公布答案並用白話說明；不論答對或答錯都可繼續，不要求重答。

測試只使用專用練習檔、測試資料夾、假姓名與學員本人可收信的報名
Email。若要刪除測試資料、建立觸發器、推送到Apps Script(clasp push)
或部署(deployment)，必須先取得使用者確認。

第 1 至 5 項由 Agent 執行並保存證據；第 6 至 9 項是學生的教學驗收。工程測試函式可以留在專案中供 Agent 回歸與除錯，但不得列成學生每課都要依序操作的作業。

## Agent-first 修改循環

每次增加功能時固定依序執行：

1. Agent 先完成「課程簡介關卡」，用白話說明用途、成果、分工、資源／設定來源、影響與驗收；若需要資源 ID，先解釋原因再進入任何設定步驟。
2. Agent 先查 `templates/catalog.json`；已有 `validated` 模板時使用 `scripts/materialize_template.py` 取用，不重新生成程式。只有 Toolbox Google 技能包維護流程中的尚未驗收課次，才在本機實作或修改程式及測試。
3. Agent 執行語法、型別、格式及可在本機完成的測試。
4. 通過驗證後，Agent 檢查敏感資料並主動建立只包含本次變更的本機 Git commit；使用者明確停用 Git 時除外。
5. Agent 說明 Git commit、待上傳檔案、目標 Script 專案及可能新增的 OAuth 權限。
6. 取得使用者確認後，Agent 才執行 `clasp push`。
7. Agent 完成工程測試，整理正常、錯誤、重複及課程特有情境的通過證據。
8. 推送成功後，Agent 在第一次學生操作指示的同一則訊息先提供「精簡課程回顧」，重述功能、可見成果、目前操作的必要性與尚未發生的外部影響，再指出本課真正會使用的 UI 入口及成功判斷方式；不得只剩操作步驟。只有必要的初始化或設定才引導 Apps Script 函式，且精簡回顧不能取代課程開始時的完整簡介。
9. 使用者親自完成一次真實 UI 流程，必要時依入口查看「執行記錄」或「執行項目」，並檢查 Google 服務中的可見成果。
10. 使用者回報自己的判讀；Agent 根據實際結果判斷完成或留在同一課修正。
11. 實際成果通過後，Agent 用一題低輸入負擔的小問題收尾；學生回答後公布答案與原因，再繼續下一個教學範例。
12. Toolbox Google 技能包維護流程在課次成為 `completed` 後，把完整累積程式沉澱為該課 `validated` 模板；一般學生專案不修改技能包。

使用者不需要複製貼上或修改程式。Agent 只提供目前驗證步驟所需的介面操作，不把程式撰寫工作轉交給使用者，也不代替使用者完成教學中的最終驗證。

Agent 預設不操作使用者的電腦或瀏覽器 UI，除非使用者明確要求。程式依功能拆分但控制檔案數量；引導必要函式時，先說明檔案、函式、用途及預期結果。
