# 部署、版本與回復流程

本流程適用於 Web App 及其他需要 Apps Script deployment 的實際專案。部署是遠端狀態變更；不論使用 UI 或 `clasp`，都必須先顯示目標與影響並取得使用者當次確認。

## 部署前

Agent 必須完成：

1. 本機強制測試與敏感資料檢查已通過，並已有可辨識的 Git commit。
2. `clasp status` 顯示的待推送檔案與目標專案正確。
3. 使用者確認 `clasp push` 後，遠端程式已更新。
4. 說明部署類型、執行身分、誰可以存取、資料範圍、新增 OAuth 權限及公開風險。
5. 建立清楚的版本說明，包含功能摘要與對應 Git commit；不得包含 Script ID、Deployment ID、私人網址或敏感值。
6. 記錄目前穩定的部署版本，作為失敗時的回復目標。

預設由使用者親自在 Apps Script UI 完成部署。Agent 依 [Apps Script 繁體中文介面用語](../../google-apps-script-teaching/references/apps-script-ui-zh-tw.md) 一次提供一個步驟，不操作 UI。只有使用者明確要求命令列部署時，Agent 才依目前安裝版本的 `clasp --help` 準備命令，並保留相同確認門檻。

## 建立首次部署

1. 使用者點擊畫面上方「部署」，選擇「新增部署作業」。
2. 在「選取類型」選擇本次需要的類型，例如「網頁應用程式」。
3. 使用者核對「新增說明」、「執行身分」與「誰可以存取」。
4. Agent 再次摘要實際公開範圍；使用者確認後才點擊「部署」。
5. 部署完成後，使用者使用「複製網頁應用程式網址」取得 `/exec` 網址。不得把網址或 Deployment ID 寫進 Git。

## 更新既有部署

每次正式更新都建立新版本，不直接失去上一個穩定版本：

1. 從「部署」進入「管理部署作業」。
2. 選取正確部署並點擊「編輯」。
3. 在「版本」選擇「建立新版本」，填寫本次版本說明。
4. Agent 顯示新版本對應的 Git commit、測試結果與影響。
5. 使用者確認後才點擊「部署」。
6. 更新後重新使用原本的實際網址完成最小冒煙測試與功能測試，不能只查看管理畫面。

## 驗證與紀錄

部署後必須記錄：

- 部署用途與類型。
- 版本編號或可辨識說明。
- 對應 Git commit。
- 執行身分與存取範圍。
- 實際測試項目與結果。
- 上一個穩定版本。

小型專案記錄在 `README.md`；複雜專案記錄在 `docs/test-report.md`。私人網址、Deployment ID 與 Script ID 只在本機或 Google 介面核對，不進入 Git。

## 回復上一個穩定版本

新版本測試失敗時：

1. 停止繼續加入修改，保存失敗紀錄檔(Log)與測試輸入。
2. 使用 `google-apps-script-debugging` 判斷是否能安全修正。
3. 若需要立即回復，Agent 顯示目前版本、上一個穩定版本、回復影響及仍可能存在的資料副作用。
4. 使用者確認後，從「管理部署作業」選取該部署、點擊「編輯」，在「版本」改選上一個已驗證版本，再點擊「部署」。
5. 使用相同實際網址重跑最小冒煙測試，確認服務已恢復。
6. 回復 deployment 不會自動還原已寫入的資料、已寄出的郵件或已建立的檔案；這些副作用必須另行盤點，不得自動刪除。

## 封存部署

只有部署已被替代、不再使用，而且使用者確認沒有依賴者後才可封存：

1. 從「部署」進入「管理部署作業」。
2. 選取目標並點擊「封存部署作業」。
3. Agent 說明封存後舊網址可能停止服務及可能受影響的使用者。
4. 使用者確認後，在詢問畫面點擊「封存」。

封存不是刪除 Git 歷史，也不代表相關資料、觸發器或 Script Properties 已移除。這些項目需要分別盤點與確認。
