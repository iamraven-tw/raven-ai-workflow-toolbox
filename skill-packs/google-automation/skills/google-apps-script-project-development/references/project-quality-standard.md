# 專案品質標準

本標準把教學技能已確立的 Script Properties、測試、繁體中文紀錄檔(Log)、重複執行與使用者驗收規則，強制套用到所有建立、接管及後續修改的實際專案。

## Script Properties 強制規則

每個專案先建立設定清單，至少記錄：

| 欄位 | 說明 |
|---|---|
| 屬性名稱 | 程式實際讀取的固定名稱 |
| 用途 | 哪項功能需要這個設定 |
| 必填 | 缺少時是否必須停止 |
| 敏感性 | 一般資源識別碼、個資或秘密 |
| 設定者 | 預設由使用者親自輸入 |

使用者可理解且需要經常調整的非敏感設定，優先放在設定工作表、側邊欄或對話框；Script Properties 保留給資源 ID、低頻技術設定與不適合顯示在日常介面的值。

執行規則：

1. Spreadsheet ID、Form ID、文件範本 ID、Folder ID、API Key 與第三方 Token 不得硬寫進原始碼。
2. 一般 Google 資源 URL／ID 等非敏感設定，若資源由 Agent 建立，Agent 必須從已核對網址擷取並直接提供完整 ID，不得要求使用者自己找網址或拆出 ID；只有使用者原有或親自建立的資源，才由使用者主動貼 URL 給 Agent。Agent 說明 ID 位於 URL 的哪一段並提供屬性名稱，最後仍由使用者親自在「專案設定」的「指令碼屬性」輸入。
3. API Key、Token、密碼及其他敏感值不得要求使用者貼進對話。Agent 只提供屬性名稱、用途與輸入位置。唯一教學例外是第二階段第 8 課：Agent 可依教學技能規則用本機安全亂數產生並顯示一次只供當課使用的 `WEBHOOK_TOKEN` 臨時教學密語，清楚說明它不適合正式使用且不得要求學生回傳；這個值仍不得進入程式、測試、紀錄檔(Log)、Git 或課程進度。
4. Google 帳號密碼、OAuth access token 與 refresh token 永遠不得存入 Script Properties。
5. Agent 必須建立集中式設定讀取與檢查函式。主要功能開始寫入、寄送、建立檔案或呼叫外部服務前，先檢查所有必要屬性。
6. 缺少設定時，以繁體中文紀錄檔(Log)說明缺少的屬性名稱與下一個操作，並在產生任何業務副作用前安全停止。
7. 紀錄檔(Log)、測試資料、錯誤畫面、Git 與交付文件只能記錄屬性名稱及「已設定／未設定」，不得保存實際值。
8. 本次功能不需要 Script Properties 時，也要明確記錄「本功能沒有必要的 Script Properties」，並檢查程式沒有硬寫私人 ID 或秘密。
9. 接管既有專案時，先盤點程式使用的屬性名稱，只確認「已設定／未設定」；未經使用者確認，不讀出、覆寫或刪除既有值。
10. Script Properties 不是專業秘密管理系統。不得保存不應讓專案編輯者接觸的機密。

## 可驗證的繁體中文紀錄檔(Log)

每個主要入口、觸發器處理函式與測試函式都必須輸出可供人類判讀的繁體中文紀錄檔(Log)。至少使用：

- `[開始]`：函式正在處理的工作。
- `[設定]`：必要設定是否齊全，不顯示實際值。
- `[成功]`：完成的結果、數量或可檢查位置。
- `[失敗]`：失敗步驟、中文原因及下一個檢查動作。

依功能需要加入 `[進度]`、`[略過]`、`[警告]`。紀錄檔(Log)必須符合：

1. 使用者只看 Apps Script 編輯器下方的「執行記錄」，也能知道本次做了什麼、成功或失敗，以及下一步。
2. 不只輸出英文例外、原始物件、`true`／`false` 或難以理解的技術訊息。
3. 錯誤可加入安全的技術摘要，但必須先有繁體中文脈絡，且不得吞掉需要讓測試失敗的例外。
4. 可記錄函式名稱、測試模式、資料筆數、處理數量、耗時及非敏感識別資訊。
5. 不得輸出 Script Properties 實際值、完整郵件、完整 Webhook 本文、OAuth 資訊、觸發器 ID 或不必要個資。

## 強制測試矩陣

每個可獨立驗收的功能至少完成：

1. **設定檢查**：必要 Script Properties 齊全時可以執行；缺少時有中文紀錄檔(Log)，且不產生副作用。
2. **正常案例**：有效測試資料產生預期結果。
3. **錯誤案例**：空白、格式錯誤或不允許的資料被拒絕；錯誤後不得繼續寫入、寄送或建立檔案。
4. **重複執行**：同一份資料或同一事件重跑，不會產生重複資料列、文件、郵件、觸發器或其他業務結果。
5. **可見結果**：使用者能在對應 Google 服務看到並判斷實際成果。
6. **可診斷結果**：「執行記錄」包含與結果相符的繁體中文紀錄檔(Log)。

依功能增加：

- 批次處理：零筆、一筆及多筆。
- 觸發器：手動測試處理函式，再讓真實觸發條件執行一次。
- Gmail：測試只寄到使用者能親自檢查的地址；實際報名專案則由已驗證
  的報名資料取得收件人，不以額外測試屬性取代業務欄位。真實寄出前
  另行確認。
- Web App／Webhook：使用實際部署網址測試正常、錯誤及重送請求。

測試只使用專用測試檔、測試資料夾、假資料及使用者自己的測試信箱，不直接破壞真實資料。

## Google Sheets 欄寬保護

所有會建立、清除或更新 Google Sheets 的程式，都要先區分「第一次建立版面」與「日常更新資料」：

1. 第一次建立工作表時，可以依需求使用 `autoResizeColumns()`、`setColumnWidth()` 或 `setColumnWidths()` 設定合理的初始欄寬。
2. 日常更新資料時，預設只更新內容與必要格式，不得再次自動調整或固定欄寬，以免覆蓋使用者手動調整的欄寬。
3. 只有需求明確規定程式每次都要控制固定版面時，才能在更新流程重設欄寬；必須先說明會覆蓋手動調整，並把這項行為列入驗收。
4. 只需更新資料時，優先使用 `clearContent()`／`clearContents()`，不要用會清除不必要版面設定的廣泛清除方式。
5. 涉及 Sheets 寫入的測試，要模擬或實際調整一次欄寬，再執行正常與重複更新，確認欄寬保持不變；程式刻意管理固定版面時則驗證預定寬度。

## Google Sheets 控制欄與最後資料列

- 核取方塊、公式、資料驗證或預填狀態欄可能讓空白列具有 `FALSE`、空字串或公式結果；不得只用這類控制欄或 `getLastRow()` 判斷真正的最後資料列。
- 新增、讀取與重複檢查資料時，必須依名稱、地址、Email、唯一識別碼等實際資料欄判斷列是否有內容，再決定讀取範圍與新增位置。
- 教學假資料要出現在學生打開工作表即可看見的前段資料列；若舊版曾因控制欄誤判而把已知教學假資料寫到遠處，只能搬移可明確辨識的教學假資料，不得清除使用者資料。
- 本機測試至少包含「控制欄已有 `FALSE`、實際資料欄仍空白」案例，確認第一筆資料寫入第 2 列，讀取時不把空白控制列算成資料。

## Google Sheets 自訂選單與 UI 執行環境

- 自訂選單統一由綁定型 Apps Script 的 `onOpen(e)` 建立，並以重新開啟或重新整理試算表作為可見結果驗收。
- 能用自訂選單滿足日常操作入口時，Agent 必須直接建立選單，使用者只需重新整理試算表並使用選單。除非按鈕本身是明確需求、驗收目標，或自訂選單無法滿足需求，不得把插入圖片、繪圖或指派指令碼轉交使用者。
- 建立工作表、寫入初始版面或檢查設定的函式不得直接呼叫 `onOpen()`，也不得把 `SpreadsheetApp.getUi()` 當成資料設定流程的一部分。
- 資料設定成功與選單載入必須分開記錄；不能因目前執行環境沒有試算表 UI，就把已完成的工作表建立判定為全部失敗。
- 本機回歸檢查應確認設定函式不含 `onOpen()` 或 `getUi()` 呼叫；遠端驗收則重新整理試算表，確認自訂選單實際出現。

## Google Docs 固定版面與文字方向

涉及信封、標籤、證書、名牌、票券或其他可列印固定版面時，必須同時使用 `google-docs-layout`；以下規則是所有專案的最低基線。

- 頁面方向只決定紙張寬高，不代表內容已完成直式或橫式排版。信封、標籤、證書及其他固定版面必須分別定義文字方向、對齊方式與資料區位置。
- 有官方或使用者提供的參考版面時，先列出可驗收的位置關係，再實作版面；不得只憑「看起來差不多」自行移動重要資料。
- Google Docs 沒有原生中文直書功能。需要中文直排時，優先用窄欄自然折行模擬文字方向，並用無框線表格固定資料區；不得在每個字後插入手動換行，程式註解與文件也要揭露這項限制。
- 直式與橫式需求不同時，使用分開的排版函式，避免用大量條件混在同一段程式而互相破壞。
- 某一方向已完成使用者目視驗收並定稿後，將其視為版面基線；開發另一方向時使用獨立尺寸與測試，不得順便重構或改動已驗收版面。
- 重寫既有文件時，要明確設定字體大小並清除不需要的粗體、斜體等文字樣式，不能依賴新元素或舊文件的繼承格式。
- 同一頁的固定版面資料區優先放在同一個表格或容器，不要把頁首、主要內容與頁尾拆成多個相鄰表格；Google Docs 可能在獨立區塊之間自動分頁。
- 固定版面優先把水平文字放入既有寬欄，不用合併儲存格製造寬度。合併會改變儲存格索引與欄跨度，可能讓內容移到前一欄；郵遞區號等不可拆文字要使用足夠欄寬及不可斷行字元。
- Google Docs 表格儲存格可能包含多個段落。多行內容的字體樣式要套用整個儲存格文字，對齊與行距則逐段設定；不得只取得第一個子段落後就宣告整格完成。
- 字體大小屬於驗收需求時，遠端測試要讀回實際 Google Docs 的文字樣式逐字確認，不能只檢查程式呼叫了 `setFontSize()`。
- 固定版面要集中定義欄寬、列高與單頁安全高度。本機測試確認預定尺寸未超標，遠端再目視確認每筆資料只佔一頁、頁首與郵遞區號沒有被推到下一頁。
- 本機測試要驗證可抽離的文字轉換、郵遞區號或尺寸邏輯，並檢查固定版面使用必要的表格、對齊與邊框設定。
- 遠端測試不能只看紀錄檔(Log)或頁面尺寸。使用者必須開啟實際 Google Docs，目視確認文字方向、位置、分頁及長文字是否被截斷或溢出。

## 預設測試形式

- 基礎 `.gs` 專案預設建立可由 Apps Script 函式選單執行的測試函式，例如 `runProjectTests()`；使用者不需要安裝或操作額外測試框架。
- Agent 同時執行本機語法、格式、敏感資料與可抽離純邏輯的檢查，但不得把本機結果當成 Google 服務已驗證。
- 測試函式使用假資料或注入的測試替身，不為了測試缺少設定而刪除真實 Script Properties。
- 寫入、寄信、觸發器與部署等遠端副作用，使用分開命名且用途清楚的測試函式；執行前先說明影響並取得確認。
- 只有專案確實需要 TypeScript、npm 套件或大量純邏輯測試時，才加入 Vitest 或同類本機測試框架；不得讓簡單 Apps Script 為了形式增加建置負擔。

## 專案文件位置

小型專案預設只使用一份 `README.md`，至少包含：

- 目標、使用方式與可見成果。
- 檔案、主要函式及執行入口。
- Script Properties 設定清單，不包含實際值。
- 測試函式、測試矩陣及最後結果。
- 觸發器、部署、OAuth 權限及已知限制。
- 最新可用 Git commit 與回復方式。

多個 Google 服務、多條使用流程、觸發器、deployment 或外部 API 視為複雜專案。此時 README 保留入口摘要，詳細內容拆成：

- `docs/project-spec.md`：需求、架構、設定清單、權限、觸發器與已知限制。
- `docs/test-report.md`：測試矩陣、遠端驗證、部署版本與回復紀錄。

不要為小型專案預先建立空白 `docs/`，也不要把 Script Properties 實際值、私人網址或測試個資寫入文件。

## 驗證門檻

1. Agent 先完成語法、格式、型別、純邏輯測試及可在本機完成的檢查。
2. 本機驗證未通過，不得建立完成版 commit，也不得要求使用者 `clasp push` 試試看。
3. 本機驗證通過後才建立本機 commit，顯示待推送摘要並取得使用者確認。
4. 推送後，由使用者親自在 Apps Script 執行指定函式、查看「執行記錄」及 Google 服務中的實際成果。
5. 遠端測試矩陣尚未完成，不得宣布功能完成。
6. 任一測試失敗時，轉用 `google-apps-script-debugging`；修正後重跑原失敗案例、正常案例、錯誤案例及重複執行案例。

## 觸發器設定函式

專案需要安裝型觸發器時，Agent 優先撰寫以下用途的函式；實際名稱可依專案調整，但必須在交付文件列明：

- 設定函式，例如 `setupProjectTriggers()`。
- 檢查函式，例如 `checkProjectTriggers()`。
- 只有確有需求時才提供移除函式，例如 `removeProjectTriggers()`。

設定函式必須：

1. 建立觸發條件前，比對處理函式、事件來源、事件類型及排程，避免重複建立。
2. 重複執行時安全略過已存在的觸發條件，並輸出 `[略過]` 中文紀錄檔(Log)。
3. 從 Script Properties 或明確的專案設定取得來源 ID，不把私人 ID 寫進程式。
4. 只建立本次需求中已宣告的觸發條件，不順便建立其他排程。
5. 輸出建立、已存在或失敗的繁體中文結果，但不輸出觸發器 ID。
6. 不得由 `onOpen`、選單載入或其他未經確認的入口偷偷執行。

Agent 必須先向使用者說明將建立的處理函式、事件來源、事件類型、執行帳號及頻率，取得確認後才引導使用者親自在 Apps Script 選擇並執行設定函式。執行後，使用者到左側「觸發條件」與「執行項目」確認真實結果。

移除函式屬於破壞性操作。Agent 必須列出將移除的範圍並另行取得確認；不得把建立與移除混在同一次執行。
