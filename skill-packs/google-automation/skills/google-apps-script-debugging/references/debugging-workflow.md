# Apps Script 全域除錯工作流程

## 適用範圍

本流程適用於 `google-apps-script-teaching` 與 `google-apps-script-project-development` 建立、接管、教學或維護的所有 Google Apps Script 專案，不限於「活動報名與通知系統」。

除錯由 AI Agent 主導：Agent 讀取程式、執行本機檢查、分析紀錄檔(Log)、提出單一假設、修改程式、補測試並建立 Git commit。使用者只負責必要的 Google 授權、提供實際畫面結果，以及確認 `clasp push`、觸發器、部署或其他遠端操作。

不得把「請使用者自己改程式」當成除錯方式。

## 核心原則

1. **先確認完整邏輯**：Agent 必須用白話重述使用者真正想完成的整套流程，取得使用者確認後才開始修改。
2. **先重現，再修正**：沒有明確的失敗案例，不憑猜測改程式。
3. **一次驗證一個假設**：避免同時改動多個不相關區域。
4. **以既有紀錄檔(Log)為第一證據**：前期建立的繁體中文紀錄檔(Log)應能還原執行路徑；程式看起來正確不代表遠端已成功執行。
5. **修正必須有回歸測試**：至少重跑原失敗案例與一筆正常案例。
6. **保留可回復版本**：修改前確認 Git 狀態，修正通過後建立本機 commit。
7. **不擴大權限解決錯誤**：不得用過寬 OAuth scopes、強制推送或公開部署掩蓋問題。
8. **不洩漏敏感資料**：紀錄檔(Log)、測試、錯誤畫面與 Git 都不得包含憑證、Token、密碼或不必要個資。

## 第一步：重述並確認完整業務邏輯

Agent 先讀取使用者說明、專案文件、主要入口、相關程式與既有紀錄檔(Log)，再用初學者能理解的白話重述整套流程。保持簡短，但至少包含：

1. 什麼事件或操作啟動流程。
2. 輸入資料從哪裡來。
3. 必要設定與資料驗證。
4. 主要判斷條件及處理順序。
5. 會寫入、建立、寄送或回傳什麼結果。
6. 重複執行時應如何處理。
7. 發生錯誤時應停止在哪裡，以及使用者應看到什麼。

建議格式：

> 我理解你希望的完整流程是：
>
> 1. 使用者完成……
> 2. 系統先檢查……
> 3. 條件符合時……
> 4. 成功後會……
> 5. 同一筆資料再次執行時……
> 6. 發生錯誤時……
>
> 請確認這套邏輯是否正確；如果有不同，請指出要修改的步驟。

這裡確認的是使用者期待的業務流程，不是照抄目前程式。Agent 可以先進行唯讀盤點與保存證據，但在使用者確認前，不得把目前程式行為當成正確需求，也不得開始修改。

使用者若修正流程，Agent 必須重新整理完整版本再請使用者確認。確認後才能區分：

- **需求邏輯問題**：原本描述的流程不是使用者真正想要的結果。
- **程式實作問題**：確認後的流程正確，但程式或設定沒有照流程執行。
- **兩者都有**：先定稿新流程，再以新流程建立失敗案例與回歸測試。

## 第二步：確認除錯目標

Agent 先取得或自行查明：

- 預期結果。
- 實際結果。
- 執行入口：手動函式、表單觸發器、時間觸發器、選單、Web App 或 Webhook。
- 實際執行的函式名稱。
- 發生時間與專案時區。
- 使用的 Google 帳號與執行身分。
- 是否只有特定資料、特定使用者或特定部署版本失敗。
- 最近一次已知正常的 Git commit 或 Apps Script 版本。

若使用者只說「不能用」，Agent 一次只要求能開始定位的最少資訊，不一次丟出長問卷。

## 第三步：保護現況

修改前必須：

1. 確認本機目錄與 `.clasp.json` 對應的是正確專案；不得輸出完整 Script ID。
2. 執行 Git 狀態檢查，辨識既有 staged、unstaged 與 untracked 內容。
3. 不提交、還原或覆蓋使用者原有變更。
4. 若目標檔案已有重疊變更，停止並說明範圍。
5. 確認本機程式與實際部署版本是否可能不同；不直接用 `clasp pull` 或強制 `clasp push` 猜測同步。

需要保存尚未上版的本次合法修改時，只 stage Agent 可明確歸屬的檔案或區塊。

## 第四步：用紀錄檔(Log)還原實際執行流程

先把已確認的完整業務流程與既有紀錄檔(Log)逐步對照：

| 流程階段 | 應看到的紀錄檔(Log) | 實際證據 |
|---|---|---|
| 啟動 | `[開始]` 與入口函式 | 是否真的進入正確函式 |
| 設定 | `[設定]` | 必要屬性是否齊全 |
| 處理 | `[進度]`、`[略過]`或`[警告]` | 最後成功完成哪一步 |
| 結束 | `[成功]`或`[失敗]` | 實際結果與下一個檢查方向 |

紀錄檔(Log)已足以指出失敗階段時，直接使用既有證據，不為了形式增加更多紀錄檔(Log)。只有無法判斷哪個分支、服務呼叫或寫入步驟失敗時，才加入最小診斷紀錄檔(Log)。

### 手動函式

主要查看 Apps Script 編輯器下方的「執行記錄」：

- `[開始]` 是否出現。
- 最後成功到哪一個 `[進度]`。
- 是否有 `[警告]`、`[略過]` 或 `[失敗]`。
- 錯誤訊息、檔名、行號及函式呼叫順序。

### 觸發器、Web App 與 Webhook

這些執行可能不在使用者眼前發生。Agent 引導查看左側「執行項目」，核對：

- 執行時間。
- 執行函式。
- 觸發來源。
- 執行狀態與持續時間。
- 對應的中文紀錄檔(Log)與例外。

部署型功能還要確認目前測試的是哪個 deployment，不以編輯器中的最新程式取代實際部署版本證據。

### 紀錄檔(Log)不足時

Agent 先說明目前缺少哪一段證據，再加入只足以驗證當前假設的診斷紀錄檔(Log)，並重現一次。優先放在：

- 主要條件分支的進入與略過位置。
- Google 服務呼叫前後。
- 寫入、寄送、建立檔案或回應前後。
- 例外被捕捉與重新拋出的位置。

不得輸出完整資料物件、API 回應、郵件內容或 Script Properties 實際值，也不得一次在每一行加入紀錄檔(Log)。

建議格式：

```javascript
console.info('[開始] 處理報名資料｜執行編號=%s｜測試模式=%s', runId, isTest);
console.info('[進度] 已完成資料驗證｜有效筆數=%s｜略過筆數=%s', validCount, skippedCount);
console.warn('[略過] 資料已經處理｜資料列=%s', rowNumber);
console.error('[失敗] 建立文件失敗｜步驟=複製範本｜原因=%s', message);
```

執行編號用於串起同一次流程的多則紀錄檔(Log)，但不得由 API Key、Token、Email 或其他敏感資料產生。

## 第五步：錯誤分類

Agent 先分類，再選擇檢查方向：

| 類型 | 優先檢查 |
|---|---|
| 語法、型別或建置 | 本機編譯、語法檢查、產物與 `.claspignore` |
| 同步錯誤 | 工作目錄、目標 Script、待推送檔案、本機與遠端差異 |
| 函式或入口錯誤 | 函式名稱、全域入口、選單、`doGet`、`doPost` |
| OAuth 或權限 | 執行帳號、實際服務、最小 scopes、重新授權需求 |
| Script Properties | 屬性名稱、已設定／未設定、作用範圍；不讀出敏感值 |
| 資源找不到 | Spreadsheet、Sheet、Form、Document、Folder 的 ID、名稱與存取權 |
| 資料錯誤 | 空值、欄位格式、欄位順序、二維陣列尺寸與型別 |
| 觸發器 | 觸發器建立者、事件類型、事件物件、時區、失敗紀錄 |
| Web App／Webhook | deployment、執行身分、存取者、HTTP 方法、輸入格式與回應 |
| 重複執行 | 唯一識別碼、處理狀態、Lock、Webhook 重送與觸發器重複事件 |
| 效能或配額 | 逐格服務呼叫、批次處理、執行時間、個人帳號配額 |
| 併發問題 | `LockService`、共享狀態、同時寫入與非原子更新 |

不得因看見權限錯誤就直接加入最大 scopes，也不得因同步失敗就使用強制推送。

`clasp push`只顯示`Skipping push`時，先檢查是否因`appsscript.json`變更而等待互動式覆寫確認。若使用者已確認同一次推送，且目標與待推送內容沒有改變，可改用互動式終端重跑並回答資訊清單提示；不得把跳過視為成功，也不得以`--force`取代原因確認。

## 第六步：建立可重現測試

修正前建立最小失敗案例：

- 使用練習檔、假資料、測試資料夾與使用者自己的測試信箱。
- 將純資料轉換邏輯拆成可在本機測試的函式。
- Apps Script 服務邊界使用小型整合測試函式。
- 涉及寫入時提供測試模式或 dry run；不得把正式寄信、刪除或公開部署當作測試。
- 記錄原本會失敗的輸入與預期中文錯誤。

至少測試：

1. 原失敗案例。
2. 一筆正常案例。
3. 一筆錯誤或空白案例。
4. 重複執行案例。
5. 涉及批次時的零筆、一筆與多筆資料。

## 第七步：最小修正

Agent 一次只實作能驗證目前假設的最小修改：

- 保留既有架構與命名，除非根因就是架構問題。
- 錯誤訊息補上繁體中文情境、失敗步驟與下一個檢查方向。
- 不把敏感值加入暫時紀錄檔(Log)。
- 不刪除資料、不寄出正式郵件、不建立或修改觸發器、不部署，除非使用者已明確確認。
- 不以吞掉例外或永遠回傳成功作為修正。

若第一個假設不成立，撤回僅屬於該假設的 Agent 修改，保留觀察結果，再測試下一個假設。不得使用破壞性 Git 指令清除使用者變更。

### 診斷紀錄檔(Log)收尾

修正驗證後，Agent 逐項檢查本次新增的紀錄檔(Log)：

- 能長期協助判斷開始、設定、進度、成功或失敗的紀錄檔(Log)，整理成繁體中文後保留。
- 只為單一假設加入、會大量重複或沒有後續診斷價值的暫時紀錄檔(Log)，在 commit 前移除。
- 所有保留紀錄檔(Log)再次檢查敏感值、完整物件、個資與無意義的英文技術輸出。

不得把所有診斷紀錄檔(Log)全部刪除，讓同一問題下次又無法判斷；也不得把大量暫時紀錄檔(Log)永久留在正式流程。

## 第八步：本機驗證與上版

修正完成後：

1. 執行語法、型別、lint、單元測試與技能或專案驗證。
2. 檢查 `appsscript.json` 與最小 OAuth scopes。
3. 檢查 `.claspignore` 實際會推送的檔案。
4. 搜尋 Token、密碼、私人 ID、完整測試個資與敏感紀錄檔(Log)。
5. 只 stage 本次 Agent 修改的檔案。
6. 執行 `git diff --cached --check` 並閱讀 staged diff。
7. 建立描述根因與修正結果的本機 Git commit。

使用者明確指示不用 Git 時才能跳過 commit，並在交付中說明沒有版本復原點。

## 第九步：遠端驗證

本機驗證與 commit 完成後：

1. 顯示目標 Script 專案、Git commit、待推送檔案及 OAuth 影響。
2. 取得使用者確認後才執行 `clasp push`。
3. 需要觸發器或 deployment 時，再次說明影響並另行取得確認。
4. 重跑原失敗案例與正常案例。
5. 查看編輯器下方的執行記錄；觸發器、Web App 或 Webhook 改看相符的執行項目。
6. 核對 Google Workspace 中的實際結果，不以命令成功或部署畫面作為完成證據。

遠端結果若仍失敗，回到錯誤分類，不連續加入未驗證的修補。

## 完成標準

只有同時符合以下條件才能宣布除錯完成：

- 使用者已確認 Agent 重述的完整業務邏輯。
- 根因已能用一句話說明。
- 原失敗案例已通過。
- 正常、錯誤及重複執行測試已通過。
- 中文紀錄檔(Log)能指出開始、進度、成功或失敗。
- 暫時診斷紀錄檔(Log)已移除；保留的紀錄檔(Log)仍具有長期診斷價值。
- 沒有新增不必要的 OAuth scopes。
- 沒有把敏感資料寫入程式、紀錄檔(Log)、測試或 Git。
- 本機 Git commit 已建立，或使用者已明確停用 Git。
- 若已遠端同步，實際 Apps Script 執行與 Google Workspace 結果已驗證。
- 未執行的 `clasp push`、觸發器、部署或正式資料測試已明確列出。

交付時回報：根因、修改內容、測試結果、紀錄檔(Log)證據、Git commit、遠端狀態與仍存在的限制。

## 停止條件

遇到下列情況先停止，不以猜測繼續：

- 無法確認正確專案、帳號、deployment 或執行入口。
- 現有未提交變更與修正目標重疊。
- 下一步需要真實密碼、Token、私人資料或過寬權限。
- 下一步會刪除資料、寄出正式郵件、建立觸發器或公開部署，但尚未確認。
- 錯誤來自組織管理員政策、服務停用或超出第一版範圍。
- 缺少原始錯誤、紀錄檔(Log)或可重現輸入，且無法用安全測試補足。

## 全域客製規則

使用者日後提出新的除錯、紀錄檔(Log)、測試、安全或上版規則時，若沒有明確限定某個專案，預設更新為此技能的全域規則，套用到所有由本技能處理的 Apps Script 專案。

若新規則只適用於特定公司、帳號、資料來源或專案，必須標示適用範圍，不得誤套到其他專案。
