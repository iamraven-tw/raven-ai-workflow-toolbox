# 平台權限選擇契約

## 預設模式

使用者第一次選取一個平台，或只說「管理我的社群」而沒有主動縮小功能時，使用 `full_management`：提出該平台目前正式支援、而且本技能包核心工作流會使用的完整權限。核心功能分為：

- `account_read`：辨識帳號、頻道、粉絲專頁或其他目標資源。
- `publish`：建立及管理平台內容。
- `public_comments`：讀取及管理公開留言或回覆。
- `analytics`：讀取帳號及內容成效。
- `direct_messages`：平台有正式管理介面時，讀取及回覆私訊。

平台沒有正式能力、帳號類型不支援，或本技能包尚未實作的功能，必須標示 `unsupported` 或未實作，不得為了湊齊五項功能而使用非公開端點或把其他功能冒充成它。

使用者說「只要」、「不要」、「先不要」或明確拒絕任一權限時，改用 `custom`。保留仍同意的權限，列出被停用的功能與依賴，不要求使用者重新回答已明確表達的選擇。

## OAuth 前的說明格式

外部變更預覽必須先以使用者能理解的功能說明，再附平台的實際 permission／scope 名稱。每一項至少列出：

1. permission／scope 的正式名稱。
2. 為什麼核心工作流需要它。
3. 它允許讀取、建立、修改或刪除什麼。
4. 它是否是另一個功能的相依權限。
5. 拒絕後哪些技能功能不可用或需改走手動流程。
6. 是否需要 App Review、Advanced Access、Business Verification、稽核或其他平台關卡。

不得以「完整存取」、「管理權限」等模糊詞取代實際名稱。平台自動附帶的基本身分權限也要揭露，但要清楚標示為平台自動授予，而不是 Agent 額外選取。

預覽核心權限後，再列與目前核心工作流相鄰、但不是預設功能的延伸權限類別，例如廣告、名單型廣告、企業資產、商務訂單、商品目錄、行動呼籲按鈕、直播、付費行銷訊息、訪客個人化資料、品牌合作與轉換事件。延伸權限預設不勾選；只問使用者是否要一併啟用，並且只有得到明確同意才加入 OAuth。

預覽結尾使用直接說法：

> 以上是我準備申請的權限。如果有任何一項不想開放，請現在告訴我；我會在 OAuth 前移除，並說明哪些功能會因此無法使用。

使用者確認的是這一份完整清單。OAuth 畫面出現未列出的 permission、缺少已確認項目或改用不同帳號／資源時，停止並產生新版預覽。

## 權限不等於動作授權

OAuth permission 只建立技術能力，不授權 Agent 立即使用所有寫入功能。發布、修改或刪除內容、回覆或傳送私訊、廣告、排程及其他遠端變更，仍由對應技能在看到實際目標與內容後另行預覽、確認、執行與讀回驗證。

## 設定紀錄

一般設定使用：

- `authorization_profile`：`full_management`、`custom` 或未選取時的 `not_selected`。
- `requested_permissions`：使用者確認要申請的實際 permission／scope 名稱。
- `declined_permissions`：使用者明確拒絕或要求移除的 permission／scope 名稱。

這些欄位只記錄非敏感授權意圖。Token、App ID、資源 ID、Cookie、Secret 與憑證位置仍不得寫入一般設定。
