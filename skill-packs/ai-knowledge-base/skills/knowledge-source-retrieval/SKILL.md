# 知識來源檢索

這個技能負責決定去哪裡找、如何整合、如何維護索引。它使用目前工作區已設定的 Provider；預設為 Graphify（知識結構）與本地 RAG（原文檢索：Ollama + LanceDB），但不得將兩者視為不可替換的永久介面。

NotebookLM 已停用：不再把資料送進 NotebookLM，也不再建立、查詢或同步 Notebook 集合。

只有實際使用預設 Provider 時，才讀取 [Provider adapter](references/provider-adapters.md)；使用其他後端時依相同能力契約完成工作。

## 最小 Provider 能力契約

- **知識結構 Provider**：能檢查狀態、建立或更新本地知識結構、查詢節點與來源、保留抽取或推論信心，並提供視覺化或明確宣告不支援。
- **有根據的原文檢索 Provider**：
  - **匯入**：能從單一收件匣讀取來源，把長篇原文保存成可追溯的原檔並建立索引，回報哪些已建立索引、哪些留給 Wiki 整理、哪些不支援或失敗。
  - **查詢與引用**：能針對已匯入原文查詢，每筆結果回傳原檔位置與段落（PDF 含頁碼），不得只回傳沒有出處的文字。
  - **狀態與錯誤**：能分辨「尚無資料」「模型或服務沒有在執行」「索引需要重建」等狀態，以明確的錯誤代碼或訊息回報，不在失敗時回傳空結果冒充查無資料。
- Provider 不得把登入秘密寫入本機索引；替換 Provider 也不得要求改寫讀書筆記、次級資料、Wiki 與引用 schema。
- Provider 能力不足時要明確回報差異，不得假裝已完成等價操作。

## 知識優先度

1. 使用者直接說出、親自閱讀、思考或與 AI 討論後保存的本地知識。
2. 可追溯至原始來源的本地次級資料。
3. 尚未由使用者充分閱讀的外部原文（`sources/external/`，經本地 RAG 查到的段落）。
4. Wiki、知識圖譜與 AI 的綜合判斷或推論。

這是預設的個人知識優先度，不代表本地舊筆記必然比新的第一方資料更正確。可驗證事實仍須比較來源品質、版本與時間。

## 三種模式

1. **知識檢索**：回答問題、找資料、比較既有觀點、查原文出處。
2. **收件匣整理**：把使用者要納入知識庫的檔案放進 `sources/inbox/`，執行 `ingest.py` 自動分流、建立索引，整理其他檔案，最後清空收件匣。
3. **索引維護**：檢查本地 RAG 狀態、處理失敗的匯入、重建索引、更新 Graphify 圖譜；具破壞性的步驟必須先取得使用者同意。

## 模式一：知識檢索

### 步驟 1：先查本機路由索引

依序讀取：

1. `sources/wiki/index.md`（含外部原文摘要頁 `ext_*.md` 的連結）
2. `sources/graphify-out/SOURCES_OVERVIEW.md`（若存在）

先依標題、主題、用途、標籤與來源摘要判斷資料可能在哪裡，不要一開始就搜尋全部原文。

創業方向、產品定位、目標客群或一人公司決策相關問題，若 `sources/strategy/solopreneur-profile.md` 存在，先讀取該設定檔；不存在時只有在目前沒有更明確任務時，才交給 `/solopreneur-profile` 引導建立。

社群經營策略、平台角色、內容規劃、互動原則或成效判斷相關問題，若 `sources/strategy/social-media-strategy-and-insights.md` 存在，同時讀取該檔案。`status: not_configured` 不得阻擋已提出的明確任務。逐篇數據與定期報告只是證據來源，不能在沒有使用者討論、補充與確認時被描述為已確認洞察。

### 步驟 2：查本地核心知識

- 定向搜尋 `sources/book-notes/`、`sources/wiki/` 與已知相關檔案。
- 知識結構存在時，可透過目前 Provider 查詢跨文件關係；Graphify 圖譜包含 `ext_*.md` 摘要頁，可用來找出哪份外部原文可能有答案，但圖譜不含原文本身。
- 找不到答案時，再定向搜尋已知相關的 `sources/references/` 資料。
- 不為一般問題無差別掃描整個 `sources/references/` 或 `sources/external/`。
- 保留知識結構 Provider 的抽取、推論、不確定性與來源標記。

### 步驟 3：判斷是否需要本地 RAG

Wiki 與 Graphify 優先。只有下列情況才查本地 RAG：

- 使用者要原文、原話、出處、精確數字或引用。
- Wiki、讀書筆記與次級資料沒有足夠細節回答。

其他情況直接用步驟 1、2 的結果回答，不為了「多查一點」而查 RAG。

### 步驟 4：查詢本地 RAG

- 在工作區根目錄執行 `sources/rag/.venv/bin/python sources/rag/scripts/query.py "問題" -k 5`，預設 `--mode hybrid`：向量相似度加上 jieba 中文斷詞的全文檢索，兩邊排名合併。Qwen3 向量模型需要的查詢指令前綴已由 `query.py` 處理，直接傳入問題即可。
- 可以先從相關的 `ext_*.md` 摘要頁確認哪份原文最可能有答案，再查詢。
- 結果不相關或查不到時直接說明，不用相近段落硬湊答案。
- 本地 RAG 未安裝、Ollama 沒有在執行或尚無任何外部原文時，停止 RAG 查詢並說明限制；仍可用本地來源完成目前能回答的部分。

### 步驟 5：整合與引用

答案必須區分：

- **使用者心得**：本地檔案與段落。
- **本地次級資料**：原始檔案、來源網址或知識結構位置。
- **外部原文**：一律標出檔案與段落標題，例如「`external/定價研究.pdf`／第 12 頁」或「`external/訂閱制筆記.md`／第三章 訂閱制」；PDF 的段落欄位由腳本標成「第 N 頁」，照實引用頁碼。
- **綜合判斷**：明確標示為綜合分析，不冒充來源原話。

來源互相矛盾時並列差異，不自動覆蓋任何一方。

### 步驟 6：交付知識結構視覺化

- 一般檢索先直接回答，不為每個單一事實附上整張圖。
- 涉及三個以上重要節點、跨文件關係、跨主題群、概念路徑、意外連結、核心節點或群聚結構時，主動提供視覺化。
- 使用者要求查看整體架構、關係圖或知識地圖時，將視覺化視為主要交付之一。
- 提供視覺化時，同時列出最值得查看的二至五個節點、主題群或關係。
- 回答本身必須完整，不能以「請自己看圖」取代結論與引用。
- 索引或視覺化可能過期時清楚標示；不得只為交付視覺化而盲目重建。
- manifest、環境或變更數量異常時，停止更新並回報。

## 模式二：收件匣整理

只有一個收件匣：`sources/inbox/`。使用者丟的檔案與 Agent 下載的資料都先放這裡。只有使用者明確要求加入、上傳或保存來源時，才執行匯入；一般問答不得自動把檔案放進知識庫。

### 步驟 1：放進收件匣

- 使用者把檔案直接交給 Agent，或已經放進 `sources/inbox/`。
- 檔案原本在其他位置時，**複製**一份到 `sources/inbox/`；絕不搬移、改名或刪除使用者的原檔。
- 網址先取得使用者同意保存，再把網頁內容存成檔案放進收件匣；遵守 `sources/references/README.md` 的著作權邊界。

### 步驟 2：執行 ingest.py 自動分流

在工作區根目錄執行 `sources/rag/.venv/bin/python sources/rag/scripts/ingest.py`，讀取 JSON 報告：

- `external`：PDF 或 6000 字以上的長文。原檔已搬到 `sources/external/`，切成約 700 字的片段（前後重疊 120 字）向量化後存進 `sources/rag/lancedb/`，並建立 `sources/wiki/ext_<檔名>.md` 摘要頁草稿，內含原檔連結。
- `wiki_pending`：自己的筆記、短文等其他檔案，仍在收件匣，交給步驟 4 整理。
- `unsupported`：不支援的格式（Word、簡報、圖片、壓縮檔等）與子資料夾，仍在收件匣；回報原因，請使用者另存成 PDF、Markdown 或純文字，子資料夾的檔案要直接放進收件匣。
- `errors`：讀不出正確文字（例如 Big5 等非 UTF-8 編碼、二進位內容、沒有文字層的 PDF）或向量化失敗的檔案，仍在收件匣。
- 只接受 `.md`、`.markdown`、`.txt`、`.pdf`、`.html`、`.htm`；`external` 項目的 `reindexed: true` 代表與 `external/` 同名檔內容相同，只以原路徑重建索引，摘要頁沿用既有的，不重寫。
- 預設門檻就是 PDF 或 6000 字；使用者明確要求時才加 `--min-chars <字數>` 或 `--all-external`（全部視為外部原文）。

### 步驟 3：補寫外部原文摘要

- 打開每份新外部原文，在對應的 `ext_*.md` 補寫三到五行摘要與關鍵詞，取代草稿中的待補文字。
- 摘要只描述原文內容，不加入使用者沒說過的心得；保留 frontmatter 與原檔連結。
- 把摘要頁連進 `sources/wiki/index.md` 或相關 Wiki 頁面。摘要與關鍵詞寫得具體，Graphify 才能把外部原文連進知識圖譜。

### 步驟 4：整理其他檔案

- `wiki_pending` 的檔案依既有規則歸檔：讀書心得交給 `/book-notes`；可演化的整理寫進 `sources/wiki/`；一般篇幅的次級資料放進 `sources/references/`。
- 內容角色不明確時先問一個問題，不猜測。
- 整理完成並確認新檔已寫入後，才從收件匣刪除該副本。

### 步驟 5：收尾

- 全部處理完後收件匣應該是空的；只有 `unsupported` 與 `errors` 的檔案留下，並向使用者回報原因與建議。
- 在 `sources/wiki/log.md` 追加匯入紀錄。
- 標記知識結構可能需要更新；是否立即執行 Graphify 更新由資料量與當次任務決定。

## 模式三：索引維護

### 本地 RAG

- Ollama 沒有在執行時，執行 `brew services start ollama` 後重試；仍失敗就回報，不宣稱成功。
- 同名但內容不同的新版本會另存成帶雜湊尾碼的新檔並另外建立索引與摘要頁；要更新舊版文件時先問使用者。內容完全相同的檔案只會以原路徑重建索引，不會重複。
- 腳本不提供刪除單一文件。整個索引損壞時，取得同意後才刪除 `sources/rag/lancedb/`，再把 `sources/external/` 的原文（不含 `README.md`）**複製**回收件匣，執行 `ingest.py`：每份都應以 `reindexed: true` 回報、沿用原路徑與既有摘要頁，收件匣副本會自動刪除。若出現帶雜湊尾碼的新檔，代表檔案內容已變，停下來回報。

### Graphify

- Graphify 分析 Wiki 與 `ext_*.md` 摘要頁；`sources/.graphifyignore` 以 `wiki/*` 加 `!wiki/ext_*.md` 讓一般 Wiki 頁面不重複進圖譜、摘要頁進圖譜，並排除 `inbox/`、`external/`、`rag/` 的原檔、待處理檔與索引。
- 新增摘要頁或 Wiki 內容後，用已安裝的 Graphify 技能做增量更新；只有更新實際成功後，才能把狀態標成最新。
- 整個重建、清空既有圖譜輸出或修改 `.graphifyignore`，必須先向使用者預覽並取得同意。

### 舊版紀錄

- 舊版留下的 Notebook 紀錄（例如 `sources/references/notebooks/`）若仍存在，只保留為歷史紀錄，不再新增、連線或同步 NotebookLM。

## 安全與破壞性操作

- 不得保存 Cookie、Token、登入狀態內容或私人憑證。
- 刪除 `sources/external/` 的原文、`ext_*.md` 摘要頁、整個本地 RAG 索引或 Graphify 圖譜輸出，必須取得使用者對明確目標的確認。
- 外部工具失敗時保留收件匣、索引與原始資料，不宣稱匯入或更新成功。
- 只清理由本流程複製進收件匣、且已確認完成歸檔的副本；不刪除使用者原始檔案。
