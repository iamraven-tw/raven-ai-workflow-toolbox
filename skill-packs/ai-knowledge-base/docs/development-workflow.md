# 私人使用與公開版本的開發邊界

## 目的

`My Real Second Brain` 的公開套件與維護者私人知識庫各自獨立修改。私人使用經驗可以作為未來版本的參考，但不會自動回饋、同步或觸發一般化工作。公開 repository 不保存任何私人案例內容。

## 兩邊的責任

| 層級 | 公開核心 | 實際案例 |
|---|---|---|
| 目錄契約 | `template/sources/` | 工作區的 `sources/` |
| 通用技能 | `skills/` | 可以保留案例專用整合的技能版本 |
| 一人公司設定 | 只有 `not_configured` 空白範本 | 實際方向、限制、優先事項與決策脈絡 |
| 社群媒體策略與洞察 | 只有 `not_configured` 空白範本與通用欄位 | 實際平台角色、報告位置、使用者判斷與已確認洞察 |
| 安裝契約 | manifest、安裝文件與 setup 技能 | 實際環境驗證與相容性回報 |
| 內容資料 | 只放空白模板與虛構範例 | 專案規則、筆記、索引、研究及衍生輸出 |

公開範本定義新安裝的起始結構，不要求私人知識庫持續與它保持相同。實際案例可以加入內容產線或其他專用目錄，公開 repository 則包含發行、授權與安裝文件。

## 準備下一個公開版本時的分類

只有維護者明確選定要公開的改進才進入這個流程：

1. **通用規則或能力**：去識別化、參數化並通過候選版驗證後，放進下一個公開版本。
2. **案例專用整合**：留在私人案例，不要求移植。
3. **私人內容與資料**：永不進入公開 repository。
4. **Provider 相容性修正**：在公開候選版更新契約與固定版本，完成獨立驗證後再發布。

## 公開候選版檢查

1. 確認公開檔案不含姓名、帳號、Notebook ID、私人網址、絕對路徑或實際來源內容。
2. 確認所有可安裝技能不含維護者專用的流程、私人位置或版本同步詢問。
3. 把必要差異改成使用者輸入、空白設定或中性的虛構範例。
4. 驗證 manifest、技能 frontmatter、Markdown fence 與所有必要來源路徑。
5. 在乾淨的暫存工作區測試 template 初始化；不得用真實案例資料測試公開安裝。

本機回歸命令：

```bash
python3 tests/validate_repository.py
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

這些結果只涵蓋靜態契約與虛構本機資料。第三方乾淨安裝、登入、遠端存取、另一臺電腦與正式支援仍是獨立關卡。

## 版本政策

公開版採人工挑選的版本快照。私人知識庫修改後不需要更新 Toolbox；Toolbox 發布新版後，也不會自動改寫任何私人知識庫。未來若維護者認為某項私人改進值得公開，再另外提出需求並走完上述候選版檢查。

建立 Git commit、push、遠端 repository 與公開發布是彼此獨立的動作；任何對外操作仍須另外取得明確核准。
